# How Claude Delta works

How Claude Delta runs one Claude Desktop per profile, tells which ones are running, gives each its own taskbar button, pin and notification-area icon, and routes `claude://` links.

The observations below were made on Claude Desktop 2.16120.0 (MSIX) and Windows 11 (build 26200). All of it relies on undocumented behavior of Claude or Windows; the build checks Claude's side (see the last section).

## Profiles

Claude Desktop is an Electron (Chromium) app, and Chromium allows one instance per user data folder. Started with another `--user-data-dir`, it runs a second, independent instance with its own sign-in.

| Profile | Data folder seen by Claude | Started with |
|---|---|---|
| Main | `%APPDATA%\Claude` | no argument, like the Start menu |
| Others | `%APPDATA%\Claude-<name>` | `--user-data-dir="%APPDATA%\Claude-<name>"` |

- Folders stay directly under `%APPDATA%`: Cowork's VM service looks for its disk image in `%APPDATA%\<folder>\vm_bundles`.
- A folder is never renamed, since Claude stores absolute paths in it. Renaming a profile only changes its display name, kept in `HKCU\Software\Claude Desktop Profiles Manager\Profiles\<folder>`.
- Claude itself uses `%APPDATA%\Claude-3p` and `%LOCALAPPDATA%\<folder>-Data`, so the names `3p`, `Data`, `...-3p` and `...-Data` are refused.
- A profile is `%APPDATA%\Claude`, or a `%APPDATA%\Claude-*` folder with an allowed name that holds a Chromium `Local State` file or was created by the manager. A folder linked elsewhere (a junction or directory symbolic link) counts once its `Local State` is reachable.

The manager's **Role** column:

| Role | Meaning |
|---|---|
| Claude icon, default | Main, which the regular Claude icon opens, and also the default profile |
| Claude icon | Main; another profile is the default one |
| Default | The profile picked with **Set as default**: it is selected for `claude://` links while Claude is closed |
| *(empty)* | Any other profile |

## Starting Claude

Claude Desktop is an MSIX package, and the way it is started matters:

| Started by | Package identity | Updates |
|---|---|---|
| `CreateProcess` on `WindowsApps\...\app\Claude.exe` | no | fail: "Can not find Squirrel" |
| Start menu, or `IApplicationActivationManager::ActivateApplication` | yes | work (MSIX updater) |

The manager uses `ActivateApplication(<family>!Claude, arguments)`: the process gets its identity and the arguments arrive untouched. `CreateProcess` is only a fallback when activation fails. Claude logs which case it is in at start-up (the `[MSIX]` lines of `main.log`).

With its identity, Claude writes to AppData through the package's private copy, `%LOCALAPPDATA%\Packages\<family>\LocalCache`:

- Main's data is in `%APPDATA%\Claude` when that folder exists, else in `LocalCache\Roaming\Claude` (Claude then logs `Filesystem virtualization active`), as on an installation whose Main profile was first opened through the package;
- a `--user-data-dir` that does not exist yet is created under `LocalCache\Roaming`, so the manager creates a profile's folder before its first start (never Main's);
- a profile's logs (`%LOCALAPPDATA%\<folder>\logs`) can land in `LocalCache\Local\<folder>\logs`: both places are read, and both are removed with the profile.

Since 2026-10-21 (measured on 3.1623) Claude moves Main's data out of its package, to `%LOCALAPPDATA%\Claude-Data\<family in lower case>` (`claude_pzs8sxrjxfjjc`), with a `.user-data-left.<family>` mark in the copy it left, and uses it there whenever that is a folder: its window's title, its sessions' scratch folders and its files are there from then on. Only Main moves: a profile started with its own `--user-data-dir` is "chosen" and stays where it is. Its logs stay in `%LOCALAPPDATA%\Claude\logs`. Entries made before the move still name their scratch folders below `%APPDATA%\Claude`, whose files moved with the rest.

The manager therefore keeps two paths per profile: the one Claude sees, `%APPDATA%\<folder>` (Main's moved folder once Claude moved it), which identifies a running instance, goes into launch arguments and matches the folders recorded in sessions; and the one files are read and written through, which is Main's `LocalCache\Roaming\Claude` when `%APPDATA%\Claude` does not exist and Claude did not move it. For a moved Main it keeps a third, the folder as it was named (`%APPDATA%\Claude`): a path below it is Main's, read in the moved folder, and a scratch folder below it is in Main's own area, so the sync neither rewrites those entries nor sends them as another profile's. Finding it never creates `%APPDATA%\Claude`. Main is still started without `--user-data-dir`.

The package is `Claude_pzs8sxrjxfjjc` (from claude.ai) or `AnthropicPBC.Claude_fnn82j28hfe8t` (Microsoft Store), else any other package named Claude.

A process started from Claude Desktop (a Claude Code terminal, for example) runs inside that package: it sees the private copy, not the real registry and AppData. Test from a process started by Explorer or WMI.

## Running profiles

A running Chromium instance owns a message-only window of class `Chrome_MessageWindow`, titled with its data folder; a second launch uses it to hand over its arguments. The manager lists those windows, without opening or locking anything. Its list's **Status** column follows them without polling: a thread waits for the main process of each profile running to end, and for a file made or removed right in the data folder of each one closed (where a starting Claude makes `lockfile`, which is never opened), and lists the windows again then, and once more a moment later; a change refreshes the window, which then watches what runs. The window's process is the profile's main process, and its most recently used Claude window is the first one in Z-order.

## Taskbar and notification area

A profile opened from the manager gets its own taskbar button with its badge, can be pinned from the manager, and shows its notification-area icon in its color, or its own picture when it has one (while Claude's **System tray** setting is on). A small watcher, `ClaudeDesktopProfilesManager.exe --watch "<folder>"`, does this while that profile's Claude runs: it only reacts to events and exits with Claude, unless Claude closed for an update (below).

The watcher knows that the profile's Claude has started when that Claude creates its `Chrome_MessageWindow`: it watches the window creations of the Claude process started for the profile, whose exit ends the wait. When that process is not known (Windows starts Claude itself after an update), it watches the profile's data folder instead, where a starting Claude creates `lockfile` right before that window. The wait lasts a minute and a half at most, a minute after an update. Renaming or recoloring a profile updates its button, pin and icon. The button shows the icon of the shortcut Windows makes by itself for it from the window's relaunch values (`User Pinned\ImplicitAppShortcuts\<id>\Claude (<name>).lnk`), not the window's own relaunch icon (measured on Claude 2.31226.1: with that shortcut's icon gone the button stays blank whatever the window carries). So that shortcut follows the profile too: on a rename or a color change, and when the watcher starts, it gets the profile's name and current icon when its icon is gone or an older one of ours (an icon the user chose for it stays while its file does), and the button reads it again through the temporary ID. A new display scale redraws the icon at the notification area's new size: the watcher's hidden window gets no `WM_DPICHANGED` then, but `WM_DISPLAYCHANGE`, and the size comes from the taskbar's own scale.

The watcher also gives the window the taskbar shows a thumbnail of (and Alt+Tab) the profile's title and icon: Claude's windows carry Claude's own title and their class's icon, which those show. The title is the profile's own when its **Edit…** dialog sets one (**Title**, `WindowTitle` in its registry key), else Claude's title with the profile's name after it, `Claude (<name>)`; the icon is the profile's, the button's. They go on the visible Chromium windows with a caption (`WM_SETTEXT`, `WM_SETICON`), never on the hidden message windows running detection reads. When Claude sets its title again (a name-change event), the watcher sets the profile's again, at most twenty times in ten seconds; a rename or a new title applies at once. The icons are the watcher's own, so before it ends with Claude still running (an uninstall, or a newer watcher taking over), the window gets Claude's title and class icon back.

A profile started without the manager (the regular Claude icon) keeps Claude's button until the manager opens it or routes a link to it: its watcher then starts. A profile already watched gets no second watcher: its watcher takes the new start over, even when it was about to end.

A profile is pinned while Windows' pin list holds an active pin whose shortcut opens that profile (or Claude's own Apps folder item, for Main). A shortcut left in the pins folder, or a pin Windows retired, does not count. The manager follows changes to the pin list, without polling.

The manager writes its pins in the form Windows itself writes them, so Windows keeps them, and leaves other applications' pins as they are. It never writes over a list in a form it does not know, nor over a change Windows made meanwhile: it starts again from the new list, three times at most. A new pin takes the place of the profile's pin, active or retired, else goes last; the profile's other active pins are dropped, since Windows would unpin them and delete the shortcut they share. When the manager opens, after it changes one of its pins' shortcuts, and when a profile is pinned again, damaged pins of its own are repaired; a pin that is fine is left exactly as it is, and an unpinned profile stays unpinned. At uninstall, the active pins of the manager and its profiles leave the list, then their shortcuts are deleted.

A profile's icon is the installed Claude icon with a badge: a disc in one of twenty colors (the first eight are the colors of release 1.1, at the same index), with the name's initial or a text of one or two characters of the user's own. A picture of the user's own can replace it: Windows' codecs (WIC) read it, so PNG, JPEG, GIF, BMP, TIFF and ICO always work and WebP or HEIF once their extension is installed; a GIF shows its first frame, since Windows' icons do not move, and an ICO its largest image (its first is often its smallest, which would grow blurred). The picture is cut to its middle square, scaled to 256 pixels and kept as `pictures\<folder>.png` in the manager's folder, so the file chosen can go; the profile records its stamp (a hash of its pixels), and a picture whose pixels do not match is not shown. The icon file's name encodes the name, color, badge text and picture stamp, so a change makes a new file (a profile without a badge text or a picture keeps the name release 1.1 gave it). The color menu lists the colors no other profile uses first, then, under a line, the others with the profiles that use them; a new profile starts with the first free one. The notification-area icon is Claude's own tray glyph in the profile's color; a profile with a picture shows the picture there.

The taskbar part is the Taskbar Module, under its own license (see `LICENSE`); the notification-area icon (`tray.c`) is not.

### Claude updates

A Claude update goes like this:

1. Claude's updater, in one of the open windows, logs `beforeQuitForUpdate handler fired, going down for update`.
2. Windows closes every Claude window to replace the package; each logs `Windows session ending (close-app) - quitting the app`.
3. Windows installs the new version and opens Claude again once, without arguments. That starts Main, within about half a minute, even when only another profile was open. The other profiles stay closed.

When its Claude exits, the watcher reads the last quit line of the profile's `main.log`. If it is one of the two above, from the last five minutes, the watcher waits, at most 2 minutes, for a Claude package other than the one that closed; changes to the user's package list and to the Apps folder wake it. Once the new package is there, Main is first given a minute to come back from Windows' own restart, and any other profile opens again at once; the watcher then watches the new window, so button, badge and notification-area color come back.

A quit from the window or the tray (`Quitting app...`, `beforeQuit:`, `willQuit:`), a Windows shutdown or a crash leaves the profile closed, as does a close for an update after which no new package comes. Opening the profile during the wait ends it. Windows shows the new package a moment after the changes that tell of it: after the close, and after each such change, it is looked for again every 2 seconds, ten times at most.

With **Open profiles again after a Claude update** unchecked in **Settings** (`ReopenAfterClaudeUpdate` 0 in `settings.ini`), a watcher leaves its profile closed after an update; Main, which Windows opens itself, is still watched again once it is open.

The manager's own **Quit** asks Claude to end the way Windows does before an update (Restart Manager), so Claude logs the same `Windows session ending (close-app)` line: the manager first tells the profile's watcher (`Taskbar_QuitComing`), which then takes the close for a quit, not for an update.

## Start menu

Install puts a **Claude Delta** folder in the user's Start menu with the manager's shortcut, made again when the manager starts if it was deleted. **Add to Start menu** puts a profile shortcut (`Claude (<name>).lnk`) in that folder and **Remove from Start menu** deletes it. Like every profile shortcut the manager makes, it is recorded, so it follows renames and colors and goes with the profile. The button looks again when the selection changes, when the window comes back to the front, and when that folder, Programs, the desktop or the pins folder changes. At uninstall the manager's shortcut goes last, once its windows are closed: the taskbar takes their icon from it.

## The manager window

The manager follows changes made outside it without polling: a thread waits for registry notifications on `HKCU\Software\Claude Desktop Profiles Manager` (names, colors, default), on `...\Shell\Associations\UrlAssociations` (the app picked for `claude://`), on the user's package list (Claude installed or updated) and on the taskbar's pin list, and for folder notifications on `%APPDATA%` (profile folders made or removed); a burst of them refreshes the window once. Coming back to the window refreshes it too.

Interface text is English or Simplified Chinese: Windows' preferred UI language when it is one of them (every Chinese locale takes the simplified catalog), else English, or the one picked in **Settings** (stored in the manager's `Language` registry value; a language an earlier version saved and no longer offered follows Windows). Profile names, session titles, paths and log messages are never translated. Text is measured with a font covering the selected script. Where the text names Claude's own interface (its Code tab, its No folder group, its Quit command, its stars), it uses Claude's words. After a change of language, what Windows shows of the program follows it, in the background: the `claude://` handler's name and description, and the tooltips of the manager's shortcut and of the profiles' shortcuts and pins.

The main window has no menu bar. At its top a toolbar, its buttons with icons from Windows' own icon font (Segoe Fluent Icons, else Segoe MDL2 Assets): **Open**, **Quit**, **Restart**; **New…**, **Edit…**, **Delete…**; **Set as default**; and last, icons alone (their caption in a tip), **Shortcuts** (desktop shortcut, shortcut elsewhere, taskbar pin, Start menu; each for every profile selected, the ones elsewhere into one folder then), a menu the program draws itself (`Theme_TrackMenu`: its own window and loop, the theme's rows, the keyboard as in Windows' menus), **Settings** (the interface language, the browser **Private sign-in…** opens in at once, its dialog shown only when that browser is gone, at a Magic link the clipboard holds (`Core_MagicLink`: `https://claude.ai/magic-link#<32 hex>:<the address in base64>`, asked, naming the address; the program's window watches the clipboard for one while it is open, `AddClipboardFormatListener`) or Claude Desktop's sign-in link copied, else at `https://claude.ai/login` (`SignInBrowser`: the program's own WebView2 window by default, or Edge, Chrome, Brave or Firefox when installed, each with the icon of its own executable in the drop-down, `THEME_CHOICE_ICON`), whether its window serves DevTools (CDP) on 127.0.0.1 (`SignInDevToolsPort`: the box writes 9222 or 0, settings.ini may name another port; off by default, as a set port makes every private sign-in open slower), how many days the session vault keeps, **Clean up sessions…**, **Back up .claude…** and its weekly copy, and whether profiles open again after a Claude update; **Apply**, enabled by a change, saves and applies without closing, and the open dialog follows a new language), and **About** (this version, then on the left help's questions and the changelog's versions by month, in a list whose headings fold; on the right a question's answer or what a version changed, and for a heading all of its own: every answer, the whole changelog, a month's versions, rendered from Markdown in a rich edit whose fonts and colors are the theme's). In the sessions view it acts on the profile shown. Beside the list, a column (the sessions view has none: its tree takes the width, and the view's button ends its search row): **Sessions view** (**Back** in the other view, each with its icon) on top, then **Sync settings…** (laid out as an export: the profiles the one with the focus syncs with, a check box each in a row at the top, then what they sync, the list on the left and its **Preview pane** on the right, and **Sync now**), **Export…** and **Import…** side by side (below) and **Repair**, **Windows MCP** (below), then the note on the default profile, and at its foot Claude Desktop's version over the state of `claude://` links, then this copy's version (the day of its updates, `yyyy.mm.dd`, its version in the changelog) and **Update** when there is one. The list's menu, drawn the same way, holds the toolbar's actions, **Sessions view** (V), **Sync now**, **Sync settings…**, merging, copying or moving every session, unlinking a session folder, **Export…**, **Import…** and **Recover sessions…**. Uninstalling goes through Settings → Apps. Open, Quit, Restart and Sync run on a thread of their own: the profiles' Claude quit, their groups made the same (the progress takes the status's place, also for the sync a profile's watcher makes when it closes, which posts it to the window), then they open. Several profiles can be selected: every action that can takes them all; **Edit…** of several sets only how their sessions are kept.

**Windows MCP** (`windowsmcp.c`) gives the profiles selected [Windows-MCP](https://github.com/CursorTouch/Windows-MCP), the MCP server through which Claude works Windows itself (its apps, windows, files, mouse and keyboard): one member of `mcpServers` in their `claude_desktop_config.json`, named `windows` (Claude calls its tools `mcp__windows__Click` and the like), `"windows": {"command": "<uvx.exe>", "args": ["--from", "<state folder>\windows-mcp-delta\<version>", "windows-mcp-delta", "serve", "--transport", "stdio"]}`, which runs windows-mcp-delta, the source this build carries, the rest of the file left as it is. An entry of ours named `windows-mcp` (its name until 2026.10.25), or one run from an older build's folder, or one whose uvx.exe is no longer where it says (Python reinstalled elsewhere, uv moved; a bare `uvx.exe` is left to PATH), is outdated: the manager rewrites such an entry of ours as it opens, with the uvx it finds then, and **Repair Windows MCP** rewrites it as `windows`, and an older build's folder goes once no entry runs from it. The person's own server named `windows-mcp` is theirs and stays. The transport is named: without it Windows-MCP takes the one its own `~/.windows-mcp/config.toml` holds (`windows-mcp auth` writes an HTTP one there) and serves HTTP on `127.0.0.1:8000`, which Claude does not speak, as it talks to its servers over stdio; Claude then waits for it ("Starting"), and once Claude quits that server stays behind holding the port, so that the next one fails to start (`WSAEADDRINUSE`, 10048). An entry of ours without it (uvx, no `--transport stdio`) is outdated: the button reads **Repair Windows MCP** and writes it again. Adding, repairing or removing also looks for servers left behind so, a `windows-mcp.exe` whose Claude is gone (up through `uvx.exe`, `uv.exe` or `cmd.exe`, the process that started it no longer runs; one a running Claude or a terminal started is left alone), and offers to end them. uv's `uvx` fetches and runs it; Claude from the Store does not see `PATH`, so the command is uvx's full path (`~\.local\bin`, `~\.cargo\bin`, WinGet's links, else `PATH`). Without uv, the manager offers its own installer (`irm https://astral.sh/uv/install.ps1 | iex`, in a PowerShell window), waits for it, then looks again. Once written, uvx fetches the server out of sight, so that Claude's first start of it does not wait for the download. Claude reads its servers when it starts: a profile open is closed for it, asked first, and opened again; when some of those selected are closed, the question also offers to change only those (`Ui_Choose`, the themed message box with a second choice), the open ones left as they are. A profile with Windows-MCP shows a computer at the end of its name in the list (`Theme_SetRowMarks`, purple; amber while it needs **Repair Windows MCP**), its tip saying which. When every profile selected has it, the button reads **Remove Windows MCP** and takes it away, the other servers kept.

**SearXNG search** (the column's button below Windows MCP, and **SearXNG search…** in the list's menu; `SearXng_Set`, `windowsmcp.c`) gives the profiles selected web search through the person's own SearXNG instance: the member `searxng` of `mcpServers`, `"searxng": {"command": "<npx.cmd>", "args": ["-y", "mcp-searxng"], "env": {"SEARXNG_URL": "<address>"}}`, with `"MCP_HTTP_ALLOW_PRIVATE_URLS": "true"` in `env` when it may reach private addresses (an instance on the person's network, or a proxy whose fake IPs give every address a private range). `npx.cmd` is named by its full path (`SearXng_FindNpx`: the PATH, else where Node.js's installer, nvm-windows and Scoop put it), as uvx is for Windows MCP, since Claude from the Store may not see the PATH a console sees; Claude runs a `.cmd` through `cmd.exe` itself. The address is made the form the server takes (`Core_SearXngUrl`: `https://` for a bare host, without the `/search` of a results page) and the one used last is kept (`settings.ini`'s `[SearXNG]`). Once set up, `npx --yes --package mcp-searxng node -e 0` runs hidden, which puts the package in npx's cache, so that Claude's first start of the server does not wait for the download. Removing takes away only an entry that runs mcp-searxng (`Core_SearXngServer`): a `searxng` of the person's own stays. As for Windows MCP, profiles open are closed for it and opened again, asked. The button sets it up at once in the profiles selected that lack it, with the address of the first profile that has it (selected first) or the one set up last, and opens the dialog (address, private addresses) only when none is known; once all of them have it, it reads **Remove SearXNG search** and takes ours away. The menu's item always opens the dialog, to change the address too. A profile with it shows a globe at its name's end, left of Windows MCP's computer (`Theme_SetRowMarks` gives a row several marks), its address in the tip. windows-mcp-delta reads its own profile's config as it starts (`hints.py`): with SearXNG there, its instructions tell Claude where the instance is and how to query it by hand in UTF-8, since Git Bash's own curl sends a Chinese query in the console's code page (GBK), which SearXNG, decoding UTF-8 as it should, reads as nonsense.

Claude's own **Windows-MCP extension** (Settings > Extensions, from Claude's directory: `ant.dir.cursortouch.windows-mcp`) is a second server with the same tools. Claude keeps an installed extension in the profile's folder as a member of `extensions` in `extensions-installations.json`, its unpacked folder under `Claude Extensions\<id>` and its settings in `Claude Extensions Settings\<id>.json`, and reads them as it starts. Setting up or repairing Windows MCP offers to uninstall that extension too, and the list's right-click menu has **Uninstall the Windows-MCP extension…** wherever it is installed: its folder and settings are deleted, as Claude's own Uninstall does (anything still running from the folder ended first, a file still held tried again for a few seconds), and its member is taken out of the file only once they are gone: a folder left there would show as installed again at Claude's next start, and one an uninstall leaves behind still counts as installed, to be finished. That profile's Claude is closed first and opened again after, asked, as for Windows MCP itself.

**Export…** writes a profile to one ZIP archive (`backup.c`): what is checked, everything at first, item by item as what to sync lists it, plus MCP servers, the sign-in and the profile's own (`profile/profile.json`: its name, note, color, badge and windows' title; `profile/picture.png`). The list is a property list (`checklist.c`): below a group's items, values of its own, here the profile's fields, a text shown in a second column and changed in an edit box over it while its row is selected, the color in a drop-down, the picture a switch, each with a box that leaves it out; the editor writes the value as it changes. Beside the list, under **Preview pane** and the name of the row selected, a pane (`IDC_PANE_LIST`, `ShowPane`) shows what that row holds, one step further out: a heading's own value, then its items (folding to their values) and its own values; an item's own value, then its values; a value's parts; a row with nothing below it, itself, its editor open. The list beside a pane is an overview (`CheckList.overview`): its items show how many values they hold, or their only one, its values how many parts, and only the pane shows those; a group's own values (the profile's own fields) stay below its heading, changed in place. The pane is a list of its own over the same values (`CheckList.pane`, made with the list and freed with its window): its boxes, switches, choices and texts change there as in the list, and its items and values fold there apart from the list (`openItems`, `paneOpen`); each list shows what the other changed (`Mirror`), an editor's text too, but for what is being typed in it. Its search box (`IDC_PANE_SEARCH`, shown or hidden by **Ctrl+F**) keeps the rows whose names or values match, as typed or as a regular expression, and the rows holding them (`MarkMatches`). The list's first row is selected at first, so that the pane shows something. Below it, **Select all**, **Select none** and **Invert** set every box at once (`CheckList_CheckAll`: the values at their leaves, each turned over for **Invert**; a value with parts and an item then follow theirs, and an item without values turns its own box). Each box is worked out once for all the rows from the values up (`ReadFacts`), and rows changed together are drawn once (`WM_SETREDRAW`). In a list whose rows fold, a name runs on over the empty value cells after it (`RunOnRight`, theme.c). The sign-in's item holds what the sign-in is, read-only (`SetupSignInValues`): config.json's account, and its OAuth token caches (`oauth:tokenCacheV2`, `oauth:tokenCache`, Electron's safeStorage) opened with the key, which give the organization, the plan and each token's scopes, expiry and refresh (`Core_ReadTokenCache`), never a token; where it opens (whether the key goes with it) and its size. Chromium holds a running profile's cookies for itself, so the export of a running profile's sign-in closes the profile first, asked when OK is pressed (`CloseForSignIn`), and opens it again once the export is written (`Backup_Reopen`). The sessions are values of their item, a box each, with when each was last used: an import takes only those checked, and only their conversations' files (an archive maps each session to its files in `conversations/<n>.json`; one of an earlier version has none, and gives them all). The settings are values too (`SyncUi_AddLayoutValues`, `syncui.c`), each part of the layout below its item, or on its row when it is the item's only one, or on its group's heading when the group has no items: true or false a switch, a string or a number a text (a number stays one), anything else what it holds, counted, with its parts one by one below it, folded at first (`CheckList_AddParts`: an object's members by their keys, a list's elements by their own text or name, a session's id by its title, three levels down, a short list of texts after the first on its row; a list or an object beyond that, or past the list's room, only counted); each part has a box of its own in an export or an import, and the setting is written again from its parts with what changed in them and without those left out (`CheckList_JsonOf`), a setting all left out as null, which takes it out of what is written (`SyncUi_LayoutChanges`, then `WithChanges`). Every row has an icon: the groups' and items' of what to sync, a setting its item's, a part what it is (a session, a folder, a list, a value). **New…** and **Edit…** (`gui.c`) show a form (`IDD_PROFILE_NEW`): the name, color, badge, **Choose picture…** and **Remove picture**, title, notes, **Sync** and **What to sync…**, the folder it has or will have, **Open at Windows sign-in**, and for a new profile **Copy settings from** the profile selected (else the default one), **Open it now to sign in** and, at the bottom left, **Save and sign in now** (the profile made, then its **Private sign-in…**); **Edit…** of several profiles shows only how they sync. The same values make a property list too (`IDD_PROFILE`, the list without boxes, with the profile's settings below), which the layout tests fill; both are made and read back by the same code. The conflicts' lists (a sync's in `syncui.c`, several backups holding the same part in `backup.c`) are that list read-only: a column per version, the one kept checked, a click or Left and Right keeping another. An export writes them as left; an import shows the backup's (of the newest that holds them) and gives the profile those checked, its other fields kept. The sign-in is the profile's cookies and web storage with the key Chromium encrypts them with: Windows protects that key in `Local State` for this user on this PC, so the archive carries it in the clear (`account-key.json`) and the sign-in opens anywhere; whoever has the file has the account. Archives of earlier versions whose key is behind a password still ask for it. **Import…** reads backups and sessions archives into the profile selected: a backup's items, everything checked at first, the rest of the profile left as it is, into a profile that is closed (what they replace is backed up first); a sessions archive's sessions, as **Import sessions…** does. Each archive is checked whole before anything changes. While profiles are dragged, four tiles show over the foot of the list (`dragout.c`, a window of their own with its own OLE drop target, drawn by `Theme_DrawDropZone`): **Export**, **Copy profile**, **Private sign-in** and, red under the pointer, **Delete**. Its window shows how far each is, pauses it, leaves it for later or cancels it (what it had copied deleted). The drag is over before the notice comes: the window waits for it as for any other message, five seconds at most (a timer), then asks what the exports hold. Every action that changes data asks first, in a sentence or two: what it changes, and that what it replaces is backed up first when it is (`SyncUi_Confirm`). Opening, quitting and restarting, which make a profile's group the same along the way, do not ask.

The main window can be resized and maximized. Its minimum size fits both interface languages and both views, so changing the language, the view or the status line never resizes it. A wider window keeps the content at a reading width, centered, and gives the lists the extra height. The Profile and Role columns start at the same width in every language and the last column takes the rest; a column the user sized keeps its width.

Every control's look comes from `theme.c`; [UI-COMPONENTS.md](UI-COMPONENTS.md) describes how to add one. Text cut short in a list, tree or label shows whole in a tooltip at once. The color selector and the sessions view's menus are Windows' own menus.

## Claude Code sessions

A Code-tab session is stored in two places:

- its conversation, the transcript: `%USERPROFILE%\.claude\projects\<project>\<id>.jsonl` (or under `CLAUDE_CONFIG_DIR` when it is set), in the Claude Code folder every profile shares;
- one entry per profile that lists it, in that profile's `claude-code-sessions\<account>\<organization>\local_<...>.json`: title, star (`isStarred`), folder, archived, last activity, and the session's earlier transcripts (`priorCliSessionIds`, `preClearCliSessionId`, `unarchivedCliSessionId`), which its size counts unless another session goes on with one. A conversation that runs out of room, or is cleared, goes on in the same entry with a new transcript (measured on 2.31226: `cliSessionId` changes, the earlier one joins `priorCliSessionIds`): the vault takes such an earlier transcript for no session of its own, which it neither deletes nor gives back (deleting it took the entry, already holding the new transcript, from the other profiles, then the new one from the first), and a removal never takes an entry that names another transcript by then. A profile can list a session twice; every entry of it is changed together.

Claude shows the entries of the account signed in (`lastKnownAccountUuid` in the profile's `config.json`; without one, the account with the latest entry) and of its organization with the latest entry; the entries of an account signed in before stay on disk but are not shown. A session without a project folder works in `<profile data>\scratch-workspaces\<account>\<organization>\scratch-...`, and Claude shows it under "no folder" only in the profile that owns that area. A session run over SSH (`sshConfig`), in WSL (`wslConfig`) or in the cloud (`cloudSessionId`, or `movedToCloud` set to anything but `null` or `false`) has its conversation elsewhere: the writable sessions list only counts it; a separate read-only catalog shows its saved metadata.

A session's `cwd` stays the path Claude recorded; opening, copying or deleting its scratch folder goes through the profile's file path (above), which differs for a virtualized Main. Paths can be longer than MAX_PATH: transcripts and entries are reached through their `\\?\` form. The Recycle Bin takes no path of MAX_PATH characters or more, so a removal that would need it for one is refused with that path, and nothing moves. A junction or directory link among the paths is removed as a link, never followed.

**Sessions >** turns the manager window to its sessions view, **< Back** turns it back. A session shows at its row's end where it runs, as Claude's sidebar does: a gray laptop on this PC, a teal cloud in the cloud, a purple phone for Remote Control, a green command prompt over SSH, a gold chat bubble for Slack, and an orange dot in its place while Claude shows it unread; an archived one has the amber archive mark before an amber title; a heading whose sessions are all chosen shows chosen. ### Local metadata and task definitions

The following formats were checked read-only in Claude Desktop 2.42304.2.0's `app.asar`. Entries pair JSON metadata with shared JSONL transcripts. `previousTitles` is a string array; `model`, `effort`, `permissionMode` and `sessionSettings` describe saved execution choices. `rewindEdges` names parent and child transcripts, and `publishedArtifacts` holds a URL with optional title, source path and update time. The execution-details view displays only selected saved fields and excludes raw prompts, environment values and MCP credentials. These values describe history, not live execution or current permission approval.

The account preset store is **`ccd-session-presets.json`**: `byAccount` maps an account to its `presets` catalog and optional `builtIns` and `seededFromDraft`. `window-state.json` stores geometry and maximize/full-screen state; `developer_settings.json` separately stores `allowDevTools`.

Historical account/organization records and SSH, WSL and cloud metadata have separate read-only browsers. Browsing them does not switch Claude's account, add a writable session or contact a remote host. A local historical transcript can be previewed or exported when its UUID and local path are valid. Search context rechecks the original query, regular expression and case against the same decoded snapshot it displays; a changed, nonmatching message is never labeled a match. Reading exports state that only the current transcript is included and describe omitted messages, branches and size limits. An artifact URL is opened only after an explicit confirmation showing its source and HTTPS target; cancelling leaves the browser closed. The manager makes no Claude API request for these tools.

A `scheduled-tasks.json` record includes `filePath`; the registry alone is not the task's instruction. Code task files normally live in `<Claude Code config>/scheduled-tasks/<id>/SKILL.md`, where the config is `CLAUDE_CONFIG_DIR` or `~/.claude`. Cowork uses a `Scheduled` directory below its resolved user-files root (`coworkUserFilesPath` when configured), or below `<profile>/cowork-managed` after its `.migrated.json` marker activates that layout. Task backups include supported local instruction files. On restore, task definitions stay disabled and require review in Claude; account-bound `scheduled-task-grants/.../artifact-publish-grants.json` is backed up for reference and never applied during restore. These are restoration rules of the manager, not a claim that copying a file grants execution permission.

### Session actions

- **Open** starts the profile, or reaches its window, with `claude://resume?session=<id>`. Claude opens the session, and first adds its entry when the profile does not list it yet (`local_<id>`).
- **Share** writes the session's entry, whole, into a profile that does not list it (`sessionsync.c`, as for several sessions): both profiles then go on with the same conversation, and the entry keeps its title, star, `isArchived` and whatever else Claude keeps in it. An open profile gets it once it closes.
- **Copy** writes a new conversation with a new id: the transcript with every `sessionId` replaced, up to its last whole line; a session without a folder gets a copy of its scratch folder in the target's own area, with every `cwd` pointed at it (Windows shows the progress of a long folder copy, which can be cancelled). The original's entry goes with it under the new ids, so the copy keeps its title, star and archived state, and goes on separately.
- **Preview** (Space, or the menu) shows the conversation read only, from its transcript (`.jsonl`, the last 8 MB of a longer one): each prompt and each reply, a tool call as `[name]` and what it works on (its description, command, file or pattern); tool results, thinking, meta lines, side chains and the plumbing of commands are left out (`Core_TranscriptLine`).
- **Rename**, **Pin** and **Delete** change that profile's entries of the session: `title` (with `titleSource` `user`), `isStarred`, or the entry itself, which goes to the Recycle Bin with Claude's own `deleted_<id>` marks (the time in ms) beside it, one for each id of the session that no other session there claims, as Claude's own delete does. A removal whose marks cannot be written counts as failed and is tried again (below): the try that finds the entry gone writes the session's mark.
- **Delete session everywhere** moves to the Recycle Bin, in one operation, what Claude's own delete removes: the session's entries in each profile (with the transcript Claude staged when it took the session in); its scratch folder, unless another session works in it; and what each of its transcripts that no other session goes on with has in Claude Code's folders (as **Clean up sessions…**'s Delete removes it). It then writes the `deleted_<id>` marks and drops the changes waiting for the session. It is refused while a profile that lists the session is open (that Claude would write it back), or while any Claude Code runs it.

Archiving stays in Claude: its own archive also cleans up the session's worktree and records it in `archived-sessions.idx`.

### Sessions between profiles

**Merge all sessions…**, **Copy all sessions to…** and **Move all sessions to…** in the list's menu, the menus of several sessions, and **Export sessions…** and **Import sessions…** (in the menu of the sessions tree; **Import…** beside the profile list takes sessions archives too) send sessions to several profiles at once. Ctrl+click and Shift+click select several profiles in the profile list too. A dialog lists the profiles checked and says what will happen; a profile not signed in to Claude yet has no entries folder and is left out.

- **Merge** gives each profile checked the sessions the others list, with the entry of the profile that used the session last: an older entry is replaced (the profile keeps its own entry id), a newer one stays.
- **Copy all sessions to** lists every session of the profiles selected in the profiles checked too (shared: the same conversations). **Move all sessions to** then takes them out of the profiles selected, their entries to the backup and Claude's `deleted_<id>` marks left beside, so that Claude does not take them in again; it is refused for a profile whose sessions are kept the same as others', whose sessions would go from those too.
- **Share** and **Copy** of several sessions write each entry instead of opening the session with a link, so no profile opens.
- **Export** writes a ZIP archive, stored rather than compressed: `manifest.json`, each session's entry, and its conversation's files in the Claude Code folder (the items Claude's own delete removes with it). **Import** adds the conversation files that are missing, never replacing one and only where a conversation keeps its files, then sends the entries to the profiles checked.

An entry sent to a profile is written as Claude writes its own: `local_<id>.json` in the folder of the account signed in and its organization, through a temporary file put in place. A running profile's entries are not written: what is sent to it waits in `pending-sync-<folder>.txt`, with the entries in `pending-sync-<folder>\`, and is made when it closes, at the moments the waiting changes below are made. Each change is checked again then: a session used there since keeps its entry, and one Claude marked deleted there stays deleted unless it was overwritten, shared or imported on purpose. A change that cannot be made then (a file in use, a backup that cannot be written) stays for the next time, five times at most, its tries at the end of its line, and until then counts as waiting, as one sent while the profile was open: dropped, the entry the profile still shows would pass for a change of its own and undo the group's newer one. A batch of changes finds once which running Claude shares the profile's entries folder, among the windows of Claude's profile folders only. What a change replaces or removes is first copied to `backups\<time>\<folder>` in the manager's folder, which keeps the latest 20. Once the plan is written again, an entry file of `pending-sync-<folder>\` that no line names (a line that could not be read) goes. A summary then says what was added, updated, removed, left as it was, and what waits for a profile to close.

A running Claude keeps its sessions in memory and writes them back: an entry changed under it is overwritten. A change to a running profile therefore waits in `%LOCALAPPDATA%\Claude Desktop Profiles Manager\pending-sessions-<folder>.txt` and is made when that profile closes: by its watcher, before the manager starts it again, or when the sessions view finds it closed. The session then shows "· waiting" after its title, and **Keep in <profile>** cancels a removal still waiting. A newer change replaces what waited of its kind, a removal replaces everything, and any other change cancels a waiting removal; at most 256 changes wait. A pending file is written to a temporary copy, flushed, then put in place, and one that cannot be read is never written over. Entry changes and pending-file rewrites share a per-profile mutex across processes; a waiting change is made only once Claude is checked closed, and a removal overtaken by Claude's start waits again. When a profile starts while Windows asks about a removal, its Claude keeps the session, and the entry goes when that Claude closes.

Claude Code records each session it runs in `<Claude Code folder>\sessions\<pid>.json` (`sessionId`, `procStart`). A session whose process still runs, with that start time, under a profile's Claude is "in use" there; one in use in two profiles at once gets a warning, since each goes on from what it read.

### Sessions kept the same, and the session vault

Claude no longer writes a profile's entries through a link: before it saves one, it refuses an entries folder that is a reparse point, or whose path leads elsewhere (`main.log` then says `Failed to save session ...: Refusing non-directory at private dir path (symlink/file plant)`). A profile whose entries folder is a junction to another profile's, as earlier versions of the manager made them, reads the shared sessions but loses every change it makes (titles, stars, the last activity that orders them, new sessions) once it closes. Such links are only read and taken away now: when the manager opens it offers, for each, to give the profile a folder of its own again (with the entries the shared one holds) and to keep its sessions the same as the other profile's instead; **Unlink sessions folder…** stays in the profile list's menu. The entries are copied beside the link first (`<folder>.cdm-new`), the link taken away only once they all are, then the copy put in its place: a copy that fails leaves the link as it was.

Profiles sync in groups: `SyncSessions` under each one's key holds its group's number (1 for the group an earlier version made), and `SyncParts` what it syncs, one bit per item (`SYNC_ITEM_*`; absent, everything), with `SyncItems` beside it by group, as an earlier version reads it (a group with any of its items; read alone, a group's items whole). **Sync** in the profile dialog (also for several profiles edited together, and for a new profile, which gets the group's sessions once it is signed in) and **Sync settings…** put the profiles in the group of the one chosen, or in a new group with it, a profile joining taking what the group syncs (Sync settings: a profile checked leaves the group it was in, one unchecked leaves this one); **Not synced**, or no profile checked, takes them out, and what they synced with it. What they sync (in Sync settings, and **What to sync** below **Sync** in the profile dialog, a list with check boxes whose groups fold, as the conflicts' list does: folded at first, but those opened before, kept as `SyncItemsOpened` in `settings.ini`; a right-click expands or collapses them all) is set for every member: a group syncs what all of its members do. Each part of a sidebar's layout belongs to one item. Sessions sync by item too: without new sessions, a profile gets only the sessions it lists already; without titles or archived states, each keeps its own (its entry's `title` and `titleSource`, or `isArchived`, `autoArchiveExempt` and Claude's list of the archived), and they are left out when entries are compared; without deletions, one deleted in a profile stays deleted there while the others go on with it. Sessions not synced at all leave the vault's list as it was, so that, synced again, a session deleted meanwhile is deleted elsewhere too and one made meanwhile goes across. A group left with one profile is none. Grouping is transitive: a profile kept the same as one of a group joins the whole group, and the Sessions column names every member. Each group's sessions are made the same each time one of its profiles closes (its watcher, after the waiting changes), before one opens through the manager, on **Sync now**, and when the manager opens. A profile of the group opened alone (no link, not from the manager) while another one runs asks to quit that one first: an open profile gets the others' changes only once it closes, which **Restart** does at once.

Each session, by its transcript id, is resolved against the last version the vault kept of the group's list (`Core_MirrorResolve`); an entry's hash leaves out its own id and, for a session without a folder, where that folder's area is: in each profile its entry, without its own id, hashed, with the time its file was written; or Claude's `deleted_<id>` mark and its time; or nothing. A profile that had that version's list and no longer lists a session took it away; one that never had the list, or whose entries folder is not the one the version knew (another path, or made since: Claude reinstalled, another account), or one of whose entries could not be read, only lacks it. An entry changed since the version wins, the one written last first, unless a deletion came later; a deletion, or a session taken away, goes from every profile; a profile that only lacks a session gets it. A profile that was open when a change was sent to it shows the old entry until it closes: as long as it has not used that session since, the change waiting for it (`pending-sync-<folder>.txt`) stands for its entry, so what it still shows is no change. `archived-sessions.idx` follows the same way.

Besides the sessions, a group keeps the same a layout of each profile, its parts listed in three tables of `sessionsync.c` with what each belongs to: Claude's settings in `claude_desktop_config.json` (under `preferences`, its window's under `epitaxyPrefs`, a few of them per account, `.<account>` after the name), values of its window's web storage, two files of its own, and its session presets (`ccd-session-presets.json`, its account's merged into the others'). Each part is resolved on its own. A member is sent the layout only when it would change something there: a part it shows as the group has it is no change, nor one it could not take as sent, the session presets merged into its account's own when they hold them already, or the page's zoom where Chromium has not made the profile's own key yet; so the same layout is not sent again at every sync. Session presets are merged rather than resolved: the group's are every member's put together in member order, never taken away nor a conflict, since Claude's window writes its account's catalog back from its own copy (measured on 3.1623: a profile's file rewritten from it as Claude started). A version keeps, for each member, what the sync last read of each part there (`seen` lines; for a member closed at the sync, what it holds once the changes are made there), and a member says something about a part only when it shows something else now: a profile that was open when a change was sent to it, or that lost the change before it closed, shows what it had, which is no change (two syncs at once, or a change lost on its way, once made a profile's empty groups pass for an edit and wiped another's). One member changed a part: its value goes to the others. Several changed it: their versions are merged element by element against the group's last version (`Core_JsonMerge`), an object member by member, a list by its items' `id` (or first string), a list of plain values as a set (what one added or removed is added or removed), so that changes to different elements all go across; a pane's layout and sizes are one element each. An element several changed each their own way is a conflict, written to `vault\conflicts\<list>.txt` with its JSON pointer (`/groups/#cg-1/name`, `#` before a list item's key) and each member's version as the person sees it. The part stays as each member has it until each of its conflicts is settled; the manager asks the person which version to keep of each element (Sync conflicts: a heading per kind of setting, a row per element, a column per member, the version written last chosen at first), the choices going to `vault\decisions\<list>.txt` and made at the next sync. The first time a part is kept (no version holds it), every member that has it counts, and members that hold it each their own way conflict too. A member with no record yet (a version written before them) is read against the group's last version, and one new to the group says nothing. A part that is each session's own (an object by `local_<id>`: a session's side pane, its cost) is resolved session by session, the latest changed winning, never a conflict, so that two sessions changed in two profiles both keep their change; only the sessions a profile lists are read and written there, and a session no profile has any more is dropped. Syncs never overlap: each takes a lock named after the state folder (`Local\ClaudeDesktopProfilesManager.Sync.<hash>`), the watcher's process included. A part written in a profile leaves what else its file or value holds as it was.

Claude's settings sync these: its sidebar's pins (`starred-local-code-sessions`, `dframe-local-slice`), its project order (`code-projects-order.<account>`) and its filter (`code-sessions-status-filter`, `code-sessions-selected-environments-v2`, `code-sessions-show-empty-projects` and `code-sessions-show-pr-status`, each `.<account>`, and `ccd-sessions-filter`, the projects chosen) in `claude_desktop_config.json`, under `preferences.epitaxyPrefs`, naming sessions by their entry's own id (`local_<id>`, `code:local_<id>`); whether links open in the preview (`epitaxy-transcript-links-in-preview`), going on after a usage limit (`autoResumeRateLimitOptIn.<account>`), each folder's permission mode and its warning confirmed (`epitaxy-folder-permission-mode.<account>`, `epitaxy-perm-mode-acks.<account>`), and, outside `epitaxyPrefs`, auto-archive (`ccAutoArchiveOnPrClose`), Cowork's switches (`coworkWebSearchEnabled`, `coworkBrowserToolsEnabled`, `coworkPreferredBrowser`, `coworkScheduledTasksEnabled`) and Code's (`ccdScheduledTasksEnabled`), Remote Control's folders (`remoteControlExcludedFolders`, `remoteControlPinnedFolders`) and Cowork's trusted folders (`localAgentModeTrustedFolders`). The window keeps a copy of each of its own settings in its web storage (`LSS-persisted.<name>`, with a `timestamp`), written alike where it has one. The vault reads them as one layout, each session named by its transcript, and keeps each of its parts the same as said above, each profile getting its own entry ids and its own account's keys, the rest of its settings as they were. A running Claude rewrites its settings all the time (a newer one adds fields to the sections): taken part by part, that rewrite changes none of the other parts.

The sidebar's manual groups and their sections (`customGroupsByScope`, `codeSidebarByScope`, each by `<account>/<organization>`), its **Edit sidebar** choices (`navPinnedIds`), the groups folded (`collapsedGroups`), how sessions are grouped and sorted (`groupByByMode`, `sortByByMode`), the filter of Recents, where Routines goes, the sidebar's width and the interface font, Claude's web UI keeps in its web storage, under `state` of the value `dframe-store`; the editor's font, code theme and text size in the value `epitaxy-editor-prefs`. The web storage holds more of what a group syncs: the window's zoom (`desktop-frame.mainViewZoomFactor.v1`), its language (`spa:locale`, `spa:locale-source`, plain text), the default model (`default-model`, plain text), Cowork's recent folders (`cowork-picker-recents`), each session's model and effort (`code-session-pills`), the sessions unread (`epitaxy-unread-v1`), the side panes' sections (`epitaxy.sessionRailSections`), the side pane's layout and each session's (`epitaxy.sidePaneStore.v1`: `tileLayout`, `lastPaneFlexByKind`, the transcript's mode, the trees shown; `tileLayoutBySession`, `expandedTileBySession`, `closedPaneSlotsBySession`, `transcriptModeBySession`, `bandHeightsBySession` by session), and each session's cost (`epitaxy-session-result:local_<id>`, a value per session). Claude's own files hold the rest: `config.json` its language (`locale`) and the zoom of the window's controls (`windowControlsZoomFactor`), Chromium's `Preferences` the page's zoom (`partition.per_host_zoom_levels`, under a key Chromium makes from the profile's folder, so each profile's own key is kept) and spelling's languages (`spellcheck.dictionaries`). These two files are written only where Claude made them. At each start it writes its groups and sections from there over its two copies, `dframe-group-scopes` and `dframe-code-sections` in `claude_desktop_config.json` and `LSS-persisted.<the same>` in the web storage: groups written into that file alone while Claude is closed are gone once it has started (measured on 2.31226, the groups of one profile written into another's file three times). So `webstore.c` reads these parts from the web storage as part of the layout, and the vault writes them there, with both copies alike (a copy's `timestamp` made now), while that Claude is closed; what else the web UI keeps there stays as it was.

The web storage is Chromium's Local Storage of `https://claude.ai`: the LevelDB database `<profile>\Local Storage\leveldb`. A key is `_https://claude.ai`, a zero byte, then the name, after a byte telling its encoding (1: Latin-1, 0: UTF-16LE); a value starts with the same byte. `CURRENT` names the manifest, whose edits name the live tables (`.ldb`), the log and the last sequence number; the log holds write batches in 32 KiB blocks of records, each with a masked CRC-32C. Reading takes every table and every log LevelDB would replay, each key's value of the highest sequence. Writing adds one write batch to the log, after its last whole record (in the next block when a write was cut short), with the next sequence number: LevelDB takes it in when it next opens, as it takes in its own last writes after a crash (measured on 2.31226: `Recovering log #3`, `Reusing old log`, the value read back by Claude). The folder is copied to the backup first; nothing is written while that Claude runs, and LevelDB's `LOCK` is never opened. Chromium's record of the origin (`META:https://claude.ai`: last change and size of its keys and values) is written in the same batch.

Claude also keeps the sidebar of each account on its server (`ccd/dframe-store` in the account's user settings) and, at each start, puts the server's groups over what its web storage holds, dropping assignments to groups the server does not list; a group written there from outside lasts until the next start (measured on 2.31226: a group written while PRO1 was closed was gone 90 s after it started). Unless `ccd-sync-pending:ccd/dframe-store` names the account it starts on (`<account>/<organization>`): then it sends what it holds to the server and clears the mark, as it does for its own edits not yet sent (measured: the group was there 5 minutes after the start, the mark cleared at once). So a sync that changes `dframe-store` writes that mark, unless `ccd-sync-owner` (the account Claude reconciled last) names another account.

Claude's startup sometimes takes a session's transcript for gone: it sets `transcriptUnavailable: true` in the entry, and may strip `cliSessionId`, which leaves the entry a row of its own (keyed by its own id). Such an entry never wins over a sound one: a sound copy of the session in another profile replaces it there, under its own id, and an entry stripped of its session's id is matched to its session by that own id. A profile that had the group's list and now lists no session (its storage wiped) is taken for one that lost its list: nothing is deleted elsewhere, and it gets the group's sessions back.

A session without a folder works in `<profile data>\scratch-workspaces\<account>\<organization>\scratch-...`, and Claude shows it under "no folder" only in the profile whose area that is. Sent to another profile of the group, its entry's `cwd` and `originCwd` name the same folder in that profile's own area, which is made with the files of the one it came from that it lacks or holds older (nothing is deleted, no link is made); its transcript stays where it is, and Claude Code finds it by its id. An entry an earlier version sent as it was moves to its own area at the next sync.

A session two profiles went on with apart since the last version (both entries changed, both with activity after it) whose transcript holds a branch for each (`Core_TranscriptBranches`: the last message each used, following `parentUuid`) is kept as two: the branch of the profile that went on first becomes a session of its own, a copy of the transcript without the lines of the other branch alone, under a new id, with that profile's entry titled "<title> (<profile>)", sent to every profile of the group; the original goes on with the latest branch. One whose transcript holds one line of conversation (one went on from the other) stays one.

The entries go through the sends above (backed up first, at once where a profile is closed, else once it closes), and the version is written only once every change was made or waits.

The vault is `vault` in the manager's folder, out of Claude's package, so a reinstalled Claude finds it: `lists\<list>\<UTC time>.txt` names each session a version lists, its entry (kept once, `objects\<hash>.json`) and the profiles that had it; `deleted.txt` names the sessions deleted (their entries' own ids and transcripts), which only **Clean up sessions…**'s Restore brings back (`SessionVault_Undelete`). A version is written only when the list changed; the versions of the last days set in **Settings** (`VaultKeepDays` in `settings.ini` of the manager's folder, 30 at first, 0 keeps them all) stay, and at least the 20 latest; an entry no version names any more goes a day after it was written, looked for at most once a day (`objects-swept` holds when), since that reads every version of every list. The group's list is `group`; a profile alone keeps one named after its folder, kept when it closes, opens or the manager opens, which only follows it: what it lost stays listed, to be recovered.

**Recover sessions…** puts a version of a profile's list back into it, closed: each session the version lists (as it was then, but not a deleted one), its `archived-sessions.idx`, and Claude's marks of the deleted sessions it does not list, so that Claude's own import of Claude Code's sessions leaves them out too. A profile of the group recovered to an older version passes it on to the others.

**Clean up sessions…** lists the transcripts in Claude Code's folder that no profile lists and no kept list names, nor any transcript a listed session goes on from: the deleted ones (a profile's `deleted_<id>` mark, or the vault's), and the ones no list ever had (made in a terminal, say) only when written more than 24 hours ago; none that a Claude Code runs now. Each row names the profiles whose kept lists had it (else "In no list"), and **Show** picks one profile's; none is checked at first, and **Select all** checks every row shown. **Restore** puts the ones checked back in each profile whose kept list had them, as that list last had them, mapped to that profile as a sync would, Claude's `deleted_<id>` marks taken away (in the other profiles too, as changes sent to them: backed up, and waiting while one is open), and out of the vault's deleted ones. **Delete** moves them, as Claude's own delete removes what a transcript has in Claude Code's folders (never a working folder: `<id>.jsonl`, the `<id>` folder, `.jsonl.pre-import`, `.ccr-tip.json`, `.precompact.json` and `.desktop-released.json` in every project folder, Claude Code's temporary folder of the session, and its `file-history`, `session-env`, `uploads`, `tasks`, `image-cache`, `debug`, `usage-data` and `startup-perf` items), to the Recycle Bin, and their ids join the vault's deleted ones; a copy of Claude Code's folder can be made first. **Back up .claude…** copies Claude Code's folder beside it as `<name>_<yyyymmdd>` (then `_2`, `_3`… that day); Windows shows the copy's progress and asks about a file in use. With **Back up once a week** checked (`WeeklyClaudeBackup`), after a Claude closes and none runs, a copy is made silently as `<name>_auto_<yyyymmdd>` when none is a week old, and only the two latest weekly copies stay.

## Opening at sign-in

**Open at Windows sign-in** puts a profile shortcut (`Claude (<name>).lnk`) in the user's Startup folder, which Windows opens at sign-in: the profile starts with its own button and icon. Claude's own start-up setting cannot do this for a profile other than Main, since it starts Claude without arguments. The shortcut is recorded like the others.

## The shield

The shield (`shield.c`) watches the IP Claude leaves by and ends Claude when that exit is not safe to use an account from. It reads the exit the way the user can see it: Cloudflare's trace (`claude.ai/cdn-cgi/trace`, then `api.anthropic.com`, `claude.com`, `www.anthropic.com` in turn — each sits behind Cloudflare, as Anthropic's servers do), whose `ip=` line is the IP the far side sees, through whatever proxy the system routes the request to. It then asks public IP-intelligence services what that IP is — `ip.net.coffee/api/iprisk`, `api.ipapi.is`, `proxycheck.io`, the first that answers setting the facts and the rest filling what it left unknown (`Core_ParseIpRisk`, in core.c, one parser per service): the country, a home or datacenter connection, VPN, proxy, Tor, an abuse history and a trust score. It also reads this PC's own network: a tunnel adapter up (`GetAdaptersAddresses`, by interface type or a Wintun/TAP/WireGuard/Clash name), a proxy app running (Clash, Mihomo, sing-box, v2ray, Xray and the like), the UDP exit a STUN server sees (`stun.l.google.com`, `Core_StunRequest`/`Core_StunMappedAddress`), which leaks when it differs from Claude's exit, and DNS: a one-off subdomain of `d.ip.net.coffee` is resolved (the HTTPS connect triggers it), and that service's authoritative DNS says which resolvers asked (`/api/dns/result/<token>`); one in a region Claude does not serve is a leak. IPv6 leaks when a physical adapter holds a public IPv6 and Windows' best route to a public IPv6 host (`GetBestInterfaceEx`, Cloudflare's DNS) goes out that adapter rather than the tunnel, while Claude leaves by IPv4.

Some facts only show, in the dialog, and never change the badge or end Claude: whether this PC's time zone (its current UTC offset against the exit region's, `Core_TimezoneOffsetMinutes`, more than two hours apart) and language (`Core_RegionLanguageMatches`) match the exit's region — a Chinese system on a US exit is the common case, and a badge that is always amber would say nothing — whether the default exit (`1.1.1.1/cdn-cgi/trace`) is in another country than Claude's, the time claude.ai and anthropic.com take to answer, and Anthropic's service status (`ip.net.coffee/claude/status.json`).

Whether Claude works at the exit is Anthropic's Supported Regions Policy (`Core_ClaudeRegionSupported`, core.c): its list of countries, each with the territories the policy counts with it, and Ukraine except the regions Russia occupies. The verdict (`Core_ShieldVerdict`) ends Claude when the exit is in an unsupported region, or breaks a rule the user set — no datacenter IP, a lowest trust score, no DNS or UDP leak, the tunnel adapter or proxy app gone, or the exit unreadable. Ending Claude is `Claude_EndAll` (claude.c): every Claude Desktop process of the package with the programs it started, and Claude Code's own `claude.exe`, ended at once; a transient notification-area icon then shows a Windows notification saying why, and goes once it is closed or times out. While the shield is stopped the manager opens no profile and its Open and Restart buttons are off (`Shield_Blocking`). **Only warn** (`warnOnly`) keeps every reason but ends nothing.

A profile can be limited to some regions: its country codes, kept in `settings.ini`'s `[ShieldRegions]` list (`<folder>	<codes>`), typed in the dialog and kept once the box loses focus, so a code half typed never counts (`Core_RegionAllowed` only takes whole two-letter codes). An exit outside them quits only that profile (`Claude_Quit`), not every Claude. The router, a process of its own with no shield thread, checks before it opens a link (`Shield_QuickBlock`): one trace, the country Cloudflare gives it, against Anthropic's regions and the profile's own; it holds the link back when either says no. The shield in the manager catches the rest on its next check. The dialog's **Recent events** lists each change of state, newest first, with its reasons.

It runs on a thread while the manager's window is open (`Shield_Start`/`Shield_Stop`), waking on network changes (`NotifyUnicastIpAddressChange`) and otherwise on a five-minute fallback; a change is given a moment to settle, and a burst folds into one check. Each check posts `WM_APP_SHIELD` to the window, which colors the corner badge (green safe, amber a concern, red stopped, gray off) and names the state in its tip; the badge opens the shield dialog (`IDD_SHIELD`), whose timer refreshes the exit, what it is, the leak checks and the rules while it is open. The rules and the on/off switch are kept in `settings.ini` (`Shield*`); the shield is off until the user turns it on. The IP checks go to the three services named; nothing is sent to Claude or Anthropic beyond the trace every browser fetches.

## Settings copy

A new profile can start with some settings of an existing one. From `claude_desktop_config.json`: `mcpServers`, `isHardwareAccelerationDisabled` and `preferences.menuBarEnabled`; from `config.json`: `locale` and `userThemeMode`. ## Updates

Releases of main (`ghupdate.c`): a day's builds of main make one release, as a day's commits make one version. CI tags it and names it after the day (`v2026.10.26`, "Claude Delta v2026.10.26"), marks it latest, and gives it that version's lines of the changelogs as its notes; each later push of the day deletes it and publishes its own build under the same tag, unless main has moved on meanwhile (that later push's build then does). Earlier releases stay as they were, the pre-releases `build-<n>` among them. `build.cmd` writes into the exe its build number (GitHub Actions' run number), its commit and its repository (`buildinfo.h`; a local build is number 0, of its origin's repository). The repository is private, so a release is found only with what the PC signs in to GitHub with, read from the PC alone: `gh auth token` (gh signed in), else `git credential fill` for github.com, its prompts off (`GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`); with neither, the copy was brought from elsewhere (`GhUpdate_Copied`): its version shows in red, and nothing is looked up or offered. When the manager opens, and when its version is clicked (a hand over it), gh lists the releases (`gh release list --json tagName,isDraft,isLatest`): the one marked latest, else the newest day's tag (`Core_NewestRelease`), then its commit, name and notes (`gh release view`, its tag's commit through the API when the release names none); with git's credential only, gh runs with it as `GH_TOKEN` (in its environment alone, wiped once used), and without gh `git ls-remote --tags` gives the newest day's tag and the commit it names (`Core_NewestReleaseRef`). The tag stays the same through a day, so a release is offered when it was built from another commit than this copy (`Core_SameCommit`) and not on an older day: it shows in a window with its notes (`IDD_UPDATE`, rendered from Markdown). **Update now** has gh download its exe into the state folder's `gh-update\<tag>`, checks it is an exe, and runs it with `--install`, as an update of a signed release does; without gh it opens the release page. **Later** keeps **Version … is available** and **Update** in the version's place, and the window shows again only for another release (`settings.ini`'s `GhBuildLater`, the checksum of its commit). A local build is offered the release only when its version is clicked: it may be the newer. gh and git run hidden, each call given a deadline; nothing runs on a timer.

When the manager opens, at most every 4 hours, it reads the tag of the latest release (`api.github.com/repos/<owner>/<repo>/releases/latest`) on a background thread. A newer one shows next to the version with an **Update** button, which downloads that release's `ClaudeDesktopProfilesManager.exe` to `%TEMP%` and checks it while keeping it open, so it cannot change before it runs: Windows must find it signed by the author (a valid signature, a trusted and unrevoked certificate whose common name is exactly the one the releases are signed with), and its file version must be the release's. Otherwise the file is deleted and nothing runs. This fork reads the releases of `leiyitong/Claude_Desktop_Profiles_Manager`, so a release of the original cannot replace it; its releases are not signed, so for one of them the manager offers to open the release page, to install it by hand. The release check gives up after about a minute, the download after about ten. The new copy then installs itself over the current one (written next to it, then put in place in one step, the old copy kept on failure), restarts the watchers, reopens the manager and deletes the download. Nothing else is sent.

## claude:// links

In the manager's own WebView2 window, a sign-in to claude.ai signs the profile in without any `claude://` link: once claude.ai sets a session cookie, the window reads all its claude.ai cookies from its own store (decrypting each with its own Local State key), and `cookies.c` writes them into the profile's Chromium cookie store with Windows' own `winsqlite3.dll`, each value sealed "v10" with the profile's own Local State key (`Core_SealSafeStorage`), replacing one of the same host, name and path; the profile's Claude is closed for it and opened again, signed in (its Claude must have run once, so its store and key exist). Claude keeps a person signed in with cookies, not a token, so no OAuth client or token exchange is involved. A browser sign-in returns to the app through a `claude://` link, and Windows gives every such link to one program. Claude accepts a sign-in only in the window that opened the browser, so with several windows open the link must reach the right one. With several profiles, the manager asks which one opens each link, the likely one selected.

### Which app opens them

Windows opens `claude://` links with the default app picked for `claude://`, kept in `HKCU\Software\Microsoft\Windows\Shell\Associations\UrlAssociations\claude\UserChoiceLatest` (current Windows 11 builds; other builds use `UserChoice`). The choice is signed (`Hash`): only Windows' chooser and Settings can write it.

The manager registers as an app for `claude://`: the ProgId `ClaudeDesktopProfilesManager.Url`, which runs `"<ClaudeDesktopProfilesManager.exe>" --url "%1"`, its capabilities, a `RegisteredApplications` value and an `ApplicationAssociationToasts` value of 0, which keeps Windows from announcing the new app. **Repair** writes that registration again; then, and after a first install, while Claude Desktop is installed and links do not open in the manager, the manager says what to pick, and on **Continue** opens an empty `claude:` link so that Windows shows its chooser (the router ignores that link). Windows shows the chooser only when no app is picked, so it first forgets another app's choice.

`HKCU\Software\Classes\claude` belongs to Claude, which rewrites it at every start: the manager leaves it alone.

### Routing a link

1. Spaces around the link are trimmed; it must start with `claude:` followed by something. Quotes, backslashes, spaces and control characters inside it are percent-encoded so it stays one argument; a link holding another kind of space (no-break, ideographic, any other Unicode space) is refused.
2. **One profile**: the link goes to it.
3. **Several profiles**: **Open a Claude link** lists them all, each open one said so, with the link shown without its query or fragment (they can hold a sign-in code). **Open** (or Enter, or a double click) gives the link to the profile chosen, which starts with it when it is closed; **Cancel** drops the link.
4. **Selected at first**: for a **sign-in link** (`login`, `auth`, `magic-link`, `sso` or `callback` in the path, not in the query or fragment), the window that opened the browser. That window logs `[Auth] Using system browser for: /login/...` in its `main.log`; the window with the latest such line from the last 15 minutes is selected, and the dialog names it. A window that did not start the sign-in ignores its link. For any other link, or a sign-in no window claims: the Claude window used last, else the default profile's window, else the first open one; with no Claude window open, the default profile.

A link reaches a running window through a second activation with the same `--user-data-dir`: Chromium's single-instance lock hands the link over and the new process exits.

### Notifications

Every profile's Claude shows its notifications under the package's one app id (`Claude_pzs8sxrjxfjjc!Claude`, set at start). One clicked while it is on screen goes to the Claude that showed it. One clicked in Windows' notification center, once that Claude has let it go, makes Windows' notification service start `app\Claude.exe <the notification's launch text>` itself, without `--user-data-dir`, its parent the svchost of the user's `WpnUserService_<id>` (measured on 2.31226): the default profile opens, whichever profile showed it. Claude registers no toast activator of its own, so nothing else can catch the click.

Each watcher runs a guard for it (`notifyguard.c`), one at a time (a named mutex hands it on when that watcher ends). It watches every process's Chromium single-instance window being made (`EVENT_OBJECT_CREATE`, out of context): one titled with the default profile's data folder, by a process whose parent is the notification service, while another profile runs, means a notification clicked there. That Claude is quit as **Quit** does (it has only just started), and the profile the notification belongs to comes forward: the one other that runs, else the one the user picks in **Open a Claude notification** (the link dialog, the window used last selected). With no other profile running the default profile was the one; started while the default profile already runs, the click only brings that window forward, and nothing tells whose notification it was.

## Files and registry

The program was called Claude Desktop Profiles Manager; it is Claude Delta now wherever its name shows (`APP_NAME`). Where it is stored keeps the earlier name (`APP_FOLDER`): its folders, its executable's name, its registry key, its `claude://` registration and its Start menu folder, so that an earlier installation goes on with its settings, profiles, shortcuts and pins. Its own Start menu shortcut is named Claude Delta; the one of the earlier name is removed when it is made.

| Program | `%LOCALAPPDATA%\Programs\Claude Desktop Profiles Manager\ClaudeDesktopProfilesManager.exe` |

## Limitations

- **The regular Claude icon opens Main**, with Claude's own button until the manager opens it or sends it a link: the Start menu and taskbar start Claude without arguments. The default profile only decides where `claude://` links go while Claude is closed.
- **After a Claude update** Windows opens Main again, even when only another profile was open. That Main keeps Claude's button unless it was open with its own before the update.
- **Sessions kept the same** reach a profile that is open only once it closes, and a session run over SSH, in WSL or in the cloud is not kept the same. The files of a session without a folder are copied to the other profiles' areas when it is sent; what changes in them later is copied again only for files missing or older there.
- **Shared Claude Code data**: `%USERPROFILE%\.claude` (or `CLAUDE_CONFIG_DIR`: Claude Code settings and memory) is the same for every profile. A `CLAUDE_CONFIG_DIR` set in a profile's own Claude settings is not followed.
- **Cowork** runs in one profile at a time: its VM is shared by the whole PC.
- **One sign-in at a time**: the newest `[Auth]` line is the one selected. A second sign-in started in another window before the first one finishes gets the first one's link selected for it: pick the first window in the dialog, or start that sign-in again.
- **Running profiles** cannot be deleted: quit them from the notification area first.
- **Deleted profiles**: a shortcut or pin to one offers to open the manager instead of starting Claude.
- **Linked folders**: deleting a profile whose folder is linked elsewhere removes the link and Claude's local files for it (`%LOCALAPPDATA%\<folder>`, `<folder>-Data`), not the folder it leads to.
- **Limits**: 32 profiles; `3p`, `Data`, `...-3p` and `...-Data` are refused as new profiles' names (they name the folder); a display name can be any text of 48 characters or fewer, without control characters.
- **Uninstall** keeps the profiles you choose in `%APPDATA%`, and a new install finds them again with default names and colors. A kept profile that was never opened and holds only the settings copied into it is removed.
- **Claude not installed**: only the MSIX packages are detected; the manager then shows **Get Claude**.

## Checking Claude's behavior

`build.cmd` runs `tests/test_claude.c`, which looks up in the installed Claude Desktop (`app.asar`, `Claude.exe`, its notification-area icons) and in the Claude Code it installed each fact this document relies on: the `claude://resume` link and the entry it makes, the quit, sign-in and virtualization log lines, where entries live and their fields, what Claude's own delete removes and the marks it leaves, the "no folder" area and its folder names, the window classes, how Claude Code finds transcripts and names project folders, its running-session records, and the local metadata, preset and task-definition formats above. `test_claude.exe --asar <app.asar>` runs only the ASAR facts, without examining any running profile. While a profile runs, it also checks the `lockfile` the watcher relies on. A Claude update that changes one of these facts makes the build fail with that fact's name; the checks read the installed files, they do not reproduce a clean installation.
